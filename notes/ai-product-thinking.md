# AI 产品认知

> 这部分是我对 AI 产品的一些理解——AI 产品有哪些形态、为什么要做、构思时最容易忽略什么，以及为什么最终沉淀出了后面那几个 skill。

---

## 一、AI 产品形态全景

### 1.1 B 端与 C 端：核心价值主张不同

| | B 端 | C 端 |
|---|---|---|
| **核心诉求** | 降本增效，可量化 ROI | 体验、创作、陪伴，感受为先 |
| **典型形态** | 智能客服、企业知识库、数据分析 Agent、流程自动化 | AI 助手、AIGC 创作工具、AI 陪伴 |
| **付费逻辑** | 企业采购，看能替代多少人力成本 | 个人订阅，看是否愿意为「更好的体验」付费 |
| **容错度** | 低——错误直接影响业务，需要人工兜底 | 相对高——生成不满意可以重来 |
| **评价标准** | 客观（准确率、处理时长、人力节省） | 主观（好不好用、生成得好不好看） |

这个差异带来的直接影响是：**B 端产品可以用「准确率」这类硬指标定义好坏，C 端 AIGC 产品必须自己建立评测体系**——因为「这条视频好不好看」既没有标准答案，也不能只看技术指标。

本文主要讨论 C 端。

### 1.2 C 端 AI 产品的四种形态

按「AI 在产品中扮演什么角色」来分，而不是按输出模态：

| 形态 | 代表产品 | AI 的角色 | 留存靠什么 |
|---|---|---|---|
| **Chatbot / AI 助手** | ChatGPT、Claude、豆包 | 对话入口，用户问、AI 答 | **习惯养成**——用户要有「遇到问题就想到打开它」的条件反射 |
| **Copilot / 增强工具** | GitHub Copilot、Notion AI、快影智能字幕 | 嵌入现有工作流，辅助局部任务 | **工作流绑定**——已经嵌进用户原有流程，不用它反而更麻烦 |
| **AIGC 创作工具** | Midjourney、Sora、快影智能剪辑 | 生产主体，用户提需求、AI 出内容 | **输出质量**——生成得好就留，生成得差就走，非常直接 |
| **Agent / 自动化** | Devin、Cursor、企业经营分析 Agent | 拆解任务、调用工具、多步执行 | **任务完成度**——能不能真的把事办完，办不完就是玩具 |

**这四种形态的留存逻辑完全不同，是做 C 端 AI 产品最容易踩的坑。**

Chatbot 类的问题是新奇感退去后用户想不起来用；AIGC 工具的问题是质量波动大，好的时候很惊艳、差的时候难以接受，用户对「差」的记忆远强于「好」。用做 Chatbot 的思路做 AIGC 工具（比如堆功能、加入口），解决不了留存问题——AIGC 工具的留存只能靠把生成质量的下限拉上去。

## 二、为什么要做 AI 产品

### 2.1 三种不同的价值创造方式

我把 AI 产品的价值分成三类，这三类对应的产品设计思路差别很大：

| 价值类型 | 本质 | 例子 | 传统产品能做吗 |
|---|---|---|---|
| **① 降低门槛** | 把原来需要技能或时间的事变简单 | 智能字幕（不用手打）、AI 简历（不会写也能写） | 部分能——模板、工具化可以缓解，但做不到个性化 |
| **② 开辟新场景** | 以前物理上不存在的功能 | 爆款视频复刻、AI 陪伴、风格迁移 | 不能——这是模型能力直接带出来的新需求 |
| **③ 激活潜在需求 + 串联全旅程** | 用户原本没有明确需求，AI 主动发现并激活，然后引导走完整条路径 | 见下方案例 | 不能——需要多轮理解和动态引导 |

### 2.2 第三类价值是最容易被低估的

**案例（面试中了解到的产品，非本人经历）**：蚂蚁在做一款面向蓝领人群的 AI 求职产品。

这个产品的关键洞察是：**蓝领人群的求职意愿本身就不强**。不是「想找工作但不会写简历」，而是「压根没在主动找」。

传统招聘产品的逻辑是「用户带着求职需求进来，我提供岗位列表」——但对这个人群，前提就不成立。

AI 能做的事是把整条链路串起来：

```
① 基于个人信息个性化推荐匹配岗位
   ↓（激发兴趣：不是「有很多工作」，而是「这个工作适合你」）
② 多轮对话说服，理解用户在哪个环节犹豫，针对性回应
   ↓（意愿从 0 到 1）
③ 用户不会写简历 → AI 生成
   ↓
④ 用户没有面试经验 → 提供面试指导、注意事项
```

**这里面每一步单独看都不新鲜，但它们能被串成一条线，只有 AI 能做到。**

传统产品只能等用户带着需求来。AI 产品可以主动把需求找出来，再带用户走完这条路。

**这个案例的另一个意义**：它解释了为什么需要 Agent 这种形态。上面这四步不是一个单点功能能完成的——需要多步骤执行、需要根据用户在每一步的反馈动态调整下一步策略，这正是 Agent 的定义。

### 2.3 但也要看到 AI 产品的留存难题

Sequoia 在 2023 年的分析里提到一组数据：**生成式 AI 应用的 DAU/MAU 中位数只有 14%**，而顶级消费类产品是 60-65%，WhatsApp 是 85%。首月留存率也显著低于同期的非 AI 应用。

原因大致有三类：

| 原因 | 影响哪类产品 |
|---|---|
| 新奇感退去后，找不到每天打开的理由 | Chatbot 类最严重 |
| 质量不稳定——好的时候惊艳，差的时候难以接受 | AIGC 工具类 |
| 缺乏内容生态或社交飞轮 | 所有类型 |

**这意味着：AI 产品的「能做」和「用户愿意持续用」之间还有很长的距离。** 做 AI 产品时，「这个功能技术上能实现」远不等于「这个功能有产品价值」。

## 三、AI 产品构思：从模型能力边界推导产品边界

这是我觉得做 AI 产品最容易被跳过、但影响最大的一步。

### 3.1 常见的错误顺序

```
❌ 先想产品功能 → 再看模型能不能实现 → 发现做不到 → 降级或砍需求
✅ 先看模型现在能做什么、做不好什么 → 再推导产品能力边界 → 明确哪些 gap 需要产品/工程弥补
```

第一种顺序的问题是：等到发现「模型做不到」的时候，需求已经排期、资源已经投入，只能被动降级。而 AI 产品的模型能力约束是硬约束，绕不过去。

### 3.2 推导框架

```
模型当前能力 → 产品可直接做什么 → 中间的 gap 由谁来补
```

不同模态的模型成熟度差异极大，这个差异直接决定了产品设计的复杂度。

| | **自然语言理解/生成（LLM）** | **视频生成** |
|---|---|---|
| **模型当前能力** | 指令遵循好、上下文理解准、幻觉可控 | 依赖精细 Prompt 约束、人物一致性不稳定、时间表达因模型而异 |
| **用户输入能直接用吗** | ✅ 能——用户的自然语言基本可以直接作为输入 | ❌ 不能——用户说的和模型需要的不是同一种语言 |
| **产品可直接做** | AI 助手、AI 问答、内容摘要、数据分析 | 不能直接做「一句话生成专业视频」 |
| **需要弥补的 gap** | 几乎没有，主要工作在场景选择和交互体验 | 必须做一层「意图 → 工程指令」的转化层 |
| **产品设计的重点** | 场景选对了就成功一半 | 中间层的质量决定产品成败 |

### 3.3 生视频场景：意图语言与工程语言的鸿沟

这是我在快影做视频生成相关功能时感受最深的一点。

**用户说的是意图语言：**
> 「帮我做个视频，主角是我自己，风格像这个爆款一样」

**模型需要的是工程语言：**
> 严格编辑 @视频1，将主体人物替换为 @图片1 中的 &lt;主体1&gt;。必须严格保持：分镜数量与顺序、每个镜头的运镜类型与速度、转场时机、构图与景别、光影色调。替换主体时保持画面位置、朝向、动作类型不变。禁止增减分镜、禁止添加原视频不存在的特效…（后接约束包）

这两者之间的距离，就是产品必须自己填的坑。

**这个 gap 在不同模态里差异巨大：**

| 模态 | 意图语言 → 模型输入的距离 |
|---|---|
| 文本生成 | 几乎为零，用户的话可以直接用 |
| 图像生成 | 中等，加一些风格词和质量词就能明显改善 |
| 视频生成 | **极大**，需要完整的结构化描述、约束体系、素材角色映射 |

**这就是为什么我最后沉淀了 Prompt 撰写 skill**——它不是「怎么写好提示词」的技巧集合，而是这个中间层的工程化方案。

### 3.4 视频生成的三个当前限制及对应产品策略

| 模型限制 | 直接推导的产品边界 | 产品/工程层面的应对 |
|---|---|---|
| **需要精细 Prompt，自然语言不能直用** | 用户无法「一句话生成专业视频」 | 做意图 → 工程指令的转化层；或者用模板把用户输入限定在可控范围内 |
| **人物一致性跨镜头不稳定** | 多镜头人物视频无法完全可控 | ① 限制用户操作范围（如复刻功能只替换主体、不重构镜头结构）② 用约束包兜底（双胞胎兜底、人物一致性包）③ 参考素材策略：大头照+全身照，禁用三视图 |
| **文字生成不可靠（乱码、错字）** | 带文字的电商类视频容易出问题 | 产品层做文字渲染覆盖，不依赖模型生成文字 |

第二条尤其值得说：**「限制用户操作范围」听起来像是产品能力弱，但实际上它是在模型能力约束下做出的正确设计。** 爆款复刻功能之所以只做「替换主体」而不做「自由重构」，正是因为后者会直接撞上人物一致性和结构稳定性的能力边界。

### 3.5 能力边界是动态的：护城河不能建在「模型做不到」上

今天的限制，6 个月后可能就被新模型解决了。人物一致性、时间控制、文字生成——这些都在快速改善。

**这带来一个和传统产品完全不同的判断：不能把竞争壁垒建立在「模型现在做不到的东西」上。**

如果一个产品的核心价值是「我们用了一堆 trick 绕过了模型的某个缺陷」，那么当下一代模型原生解决这个缺陷时，这个价值就归零了。

真正可能形成壁垒的是：

| 壁垒来源 | 为什么模型迭代不会摧毁它 |
|---|---|
| **工作流** | 用户已经把产品嵌进了自己的流程，切换成本高 |
| **用户数据与个性化** | 积累的是用户偏好和历史，不是模型能力 |
| **场景理解深度** | 知道这个垂类的用户到底要什么，这是产品认知不是技术能力 |

（Sequoia 在 2023 年的复盘里也提到了同样的判断：他们原本认为数据飞轮是护城河，后来发现「moats 在客户和工作流里，不在数据里」。）

## 四、C 端 AIGC 产品的核心工作环节

前面讲的都是「怎么想」，这部分是「实际在做什么」。

需要说明的是：**下面这几个环节不是 AI 产品工作的完整清单，而是我在 C 端 AIGC 工具这个具体产品形态里，感受到最需要方法论沉淀的部分。** 换一个产品形态（比如 B 端 Agent 或 AI 助手），重心可能完全不同。

### 4.1 需求价值论证：为什么要做这个 AI 需求

AI 需求最容易出现的问题是：**「技术上能做」被当成了「值得做」的理由。**

因为模型能力更新很快，很容易出现「新模型支持 XX 能力了，我们也做一个」这样的需求。但这类需求往往缺乏对用户价值的论证。

我的判断顺序是：从市场（这个方向是不是有真实需求）→ 公司（我们做这件事有没有优势）→ 用户（目标用户是谁、在什么场景下用）→ 竞品（别人怎么做的、我们的差异在哪）四层收窄。

这一层更像是一个**思考清单**，而不是可执行的 skill——每一层的内容都高度依赖具体的产品和市场认知，很难抽象成通用步骤。

### 4.2 Prompt 撰写：填平意图语言与工程语言的鸿沟

前面 3.3 说过，这是生成类产品最核心的中间层。

它可以 skill 化，是因为：
- 输入明确（用户想要什么样的 Prompt）
- 步骤可执行（判定类型 → 素材映射 → 歧义拦截 → 挂约束包 → 自检）
- 输出可验证（生成的 Prompt 能不能直接用）

→ [Prompt 撰写 skill](../skills/prompt-writing/SKILL.md)

### 4.3 效果评测：把「好不好」变成可判定的东西

C 端 AIGC 产品的评测难点在于**用户感受到的是整体效果，但改进必须落到具体环节。**

只打总分知道好不好但不知道改哪里；只看节点技术指标每个都达标但合起来还是不好看。所以需要按维度拆解，并且给每个维度写可判定的锚点描述。

这一层能 skill 化，是因为「拆维度 → 定判定标准 → 算一致率 → 看失败模式分布」这个流程本身是高度可迁移的，换产品换场景都适用。

→ [效果评测框架](../skills/evaluation/SKILL.md)

### 4.4 那些没能做成 skill 的

有些环节我尝试过整理，但最后判断它们更适合作为经验而不是 skill：

| 环节 | 为什么难 skill 化 |
|---|---|
| **模型选型** | 「能力匹配 → 性能时延 → 成本」这个收窄顺序有价值，但每一步的判断都依赖具体场景，更像决策框架而非可执行步骤 |
| **灰度放量** | 什么指标达到什么阈值才能扩量，这是场景特定的管理决策，本质是经验积累 |

**判断一件事能不能做成 skill 的标准**：有没有明确的输入、可执行的步骤、可验证的输出。三者缺一，就是框架或清单，不是 skill。
