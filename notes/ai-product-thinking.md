# AI 产品认知

> 目前市面上的AI产品大致可分为B端产品和C端产品。其中Tob B的AI主要是做生产力基础设施，将大模型能力嵌入进企业工作流中，价值主要体现在生产力和ROI上。To C的AI则更注重产品的场景创新、用户体验与分发能力。这篇主要从我接触更多的C端应用产品出发，从AI助手到AI创作工具再延生到特定领域的Agent理解AI产品。

---

## 一、AI 产品形态认知

从Chatbot到Copilot到AIGC再到Agent，每一次底层技术架构的革新都会给产品带来新的形态与体验。Chatbot以llm为底层技术，以对话为主要交互方式,常用场景有知识问答、情绪交流等。这类产品建构重点在背后的知识库以及上下文记忆。Copilot主要是在现有工作流中嵌入AI能力，需要判断AI能优化哪个步骤以及介入时机。AIGC胜负在底层模型能力以及价格，需要找到垂直场景的差异化切入点。Agent的核心则是自主规划自主执行，真实性与稳定性是关注重点。

| 形态 | 代表产品 | AI 的角色 | 留存靠什么 |
|---|---|---|---|
| **Chatbot / AI 助手** | ChatGPT、Claude、豆包 | 对话入口，用户问、AI 答 | **习惯养成**——用户要有「遇到问题就想到打开它」的条件反射 |
| **Copilot / 增强工具** | GitHub Copilot、Notion AI、快影智能字幕 | 嵌入现有工作流，辅助局部任务 | **工作流绑定**——已经嵌进用户原有流程，能极大提升原有产品效率 |
| **AIGC 创作工具** | Midjourney、Sora、可灵 | 生产主体，用户提需求、AI 出内容 | **输出质量**——生成得好就留，生成得差就走，非常直接 |
| **Agent / 自动化执行** | Devin、Cursor、企业经营分析 Agent | 拆解任务、调用工具、多步执行 | **任务完成度**——能不能真的把事办完，办不完就是玩具 |

## 二、为什么要做 AI 产品以及什么时候需要做

### 2.1 三种不同的价值创造方式

分清形态后，还需要回答哪些需求值得引入AI能力以及AI能创造哪些需求。我把 AI 产品的价值分成三类：

| 价值类型 | 本质 | 例子 | 传统产品能做吗 |
|---|---|---|---|
| **① 降低使用门槛** | 把原来需要技能或时间的事变简单 | 智能字幕（不用手动输入）、AI 简历（不会写也能写） | 部分能——模板、工具化可以解决，但做不到个性化和灵活化 |
| **② 开辟新场景** | 以前不存在的功能产品 | 爆款视频复刻、AI 陪伴、风格迁移 | 不能——这是模型能力直接带出来的新需求 |
| **③ 激活潜在需求 ** | 用户原本没有明确需求，AI 主动发现并激活，然后引导走完整条路径 | 见下方案例 | 不能——需要多轮理解和动态引导 |

### 2.2 第三类价值是最容易被低估的

**案例**：蚂蚁在做一款面向蓝领人群的 AI 求职产品。

这个产品的关键洞察是：**蓝领人群的求职意愿本身就不强**。不是「想找工作但不会写简历」，而是「压根没在主动找」。

传统招聘产品的逻辑是「用户带着求职需求进来，我提供岗位列表」——但对这个人群，前提就不成立。

AI 能做的事是把整条链路串起来：

```
① 基于个人信息个性化推荐匹配岗位
   ↓（激发兴趣：不是「有很多工作」，而是「这个工作适合你」）
② 多轮对话说服，理解用户在哪个环节犹豫，针对性回应
   ↓（意愿从 0 到 1）
③ 用户不会写简历 → AI 生成
   ↓
④ 用户没有面试经验 → 提供面试指导、注意事项
```

**这里面每一步单独看都不新鲜，但它们能被AI串成一条线，极大降低了用户的操作成本与心智畏难。**

传统产品只能等用户带着需求来。AI 产品可以主动把需求找出来，再带用户走完这条路。


### 2.3 但也要看到 AI 产品的留存难题

Sequoia 在 2023 年的分析里提到一组数据：**生成式 AI 应用的 DAU/MAU 中位数只有 14%**，而顶级消费类产品是 60-65%，WhatsApp 是 85%。首月留存率也显著低于同期的非 AI 应用。

原因大致有三类：

| 原因 | 影响哪类产品 |
|---|---|
| 新奇感退去后，找不到每天使用的理由 | Chatbot 类最严重 |
| 生成效果开盲盒——好的时候惊艳，差的时候难以接受，而每次开盲盒都需要真实付费 | AIGC 工具类 |
| 缺乏内容生态或社交飞轮 | 所有类型 |

**这意味着：AI 产品的「能做」和「用户愿意持续用」之间还有很长的距离。** 做 AI 产品时，「这个功能技术上能实现」远不等于「这个功能有产品价值」。

## 三、AI 产品构思：模型能力和产品边界的互相推导过程

这是我觉得做 AI 产品最容易被跳过、但影响最大的一步。

### 3.1 常见的思考顺序

```
先想产品功能 → 再看模型能不能实现 → 发现做不到 → 降级或砍需求
先看模型现在能做什么、做不好什么 → 再推导产品能力边界 → 产品功能受限

第一种顺序的问题是：等到发现「模型做不到」的时候，需求已经排期、资源已经投入，只能被动降级。而 AI 产品的模型能力约束是硬约束，绕不过去。
第二种顺序的问题是：过于受到限制而失去可能性。模型迭代速度极快，今天的限制，一周后就被新模型解决了。完全按当下能力设计，会失去部分产品价值。

```
### 3.2 推导框架

```
锚定用户和市场价值 → 模型当前能力 → 产品可直接做什么 → 中间的 gap 怎么补谁来补 → 决策产品约束/工程绕过/暂定
```

不同模态的模型成熟度差异极大，这个差异直接决定了产品设计的复杂度。

|  | **自然语言理解/生成（LLM）** | **图像理解/生成（多模态）** | **视频理解/生成（多模态）** |
|---|---|---|---|
| **模型当前能力** | 指令遵循好、上下文理解准、幻觉可控 | 风格迁移与美学生成较成熟，但需要 Prompt 约束 | 视频理解能力较差，精细化改动能力弱、字幕生成效果不佳 |
| **需要弥补的 gap** | 建立行业 know-how；结果与特定业务上下文的结合 | 风格/质量把控、个性化信息注入 | 意图到工程指令的转化、文字消除处理等 |
| **产品决策的重点** | 现有资源能否整理为行业知识 | 如何拉开与市面上生图产品的差异化 | 意图到工程指令的转化得好不好，能否通过工程化手段弥补模型能力的局限 |

### 3.3 例子：生视频场景中意图语言与工程语言的鸿沟

**用户说的是意图语言：**
> 「帮我做个视频，主角是我自己，风格像这个爆款一样」

**模型需要的是工程语言：**
> 严格编辑 @视频1，将主体人物替换为 @图片1 中的 &lt;主体1&gt;。必须严格保持：分镜数量与顺序、每个镜头的运镜类型与速度、转场时机、构图与景别、光影色调。替换主体时保持画面位置、朝向、动作类型不变。禁止增减分镜、禁止添加原视频不存在的特效…（后接约束包）

这两者之间的距离，就是产品必须自己填的坑。

**这就是为什么我最后沉淀了 Prompt 撰写 skill**——它不是「怎么写好提示词」的技巧集合，而是这个中间层的工程化方案。


### 3.4 应用产品的「护城河」不在模型能力上

今天的限制，6 个月后可能就被新模型解决了。人物一致性、时间控制、文字生成——这些都在快速改善。

**这带来一个和传统产品完全不同的判断：不能把竞争壁垒建立在「模型现在做不到的东西」上。**

真正可能形成壁垒的是：

| 壁垒来源 | 为什么模型迭代不会摧毁它 |
|---|---|
| **工作流** | 用户已经把产品嵌进了自己的流程，切换成本高 |
| **用户数据与个性化** | 积累的是用户偏好和历史，不是模型能力 |
| **场景理解深度** | 知道这个垂类的用户到底要什么，这是产品认知不是技术能力 |

（Sequoia 在 2023 年的复盘里也提到了同样的判断：他们原本认为数据飞轮是护城河，后来发现「moats 在客户和工作流里，不在数据里」。）

## 四、C 端产品的核心工作环节

前面讲的都是「怎么想」，这部分是我实际「接触了哪些环节」。

需要说明的是：**下面这几个环节不是 AI 产品工作的完整清单，而是我在 C 端部分应用产品形态里，感受到可以进行方法论沉淀的部分。** 换一个产品形态，重心可能完全不同。

### 4.1 需求价值论证：为什么要做这个 AI 需求

AI 需求最容易出现的问题是：**「技术上能做」被当成了「值得做」的理由。**

因为模型能力更新很快，很容易出现「新模型支持 XX 能力了，我们也做一个」这样的需求。但这类需求往往缺乏对用户价值的论证。

我的判断顺序是：从市场（这个方向是不是有真实需求）→ 公司（我们做这件事有没有基础或者优势）→ 用户（目标用户是谁、使用痛点和使用场景是什么）→ 竞品（别人怎么做的、我们的差异在哪）→ 商业化（用户是否愿意买单以及ROI能达到多少）五层进行论证。

### 4.2 模型选型：在「质量、成本和时延约束下」选择最适合当下场景的模型

模型选型也是工作中比较重要的一环，它不只是一个技术决策，同时也需要考虑到产品功能边界和运营成本。选型时需要同时考虑以下几个维度：

**① 能力匹配：不只看优势，也要看缺陷**

不同模型擅长任务不同：有的主要处理文本、有的支持图像、音频、视频；即使都是多模态模型，优势也有不同，有的指令遵循更好，有的字幕处理能力更好，有的更擅长叙事编排等。

注意在选择模型时不只考虑其优势，还要关注其缺陷。比如在视频复刻场景中，初期接入了当时公认最强生视频模型 Seedance 2.0，但在提测阶段发现该模型在竖屏视频的字幕消除能力很差，常规提示词办法无法消除原视频的文字残留。这在电商短视频里是高频问题，如果在早期模型选型评估时发现，就能提前做预处理。

**② 成本控制：按任务分级，不用一把锤子钉所有钉子**

文字理解、字段抽取和图像生成，对模型的要求不同。用高成本模型处理所有任务，可能增加支出，却没有带来相应的效果提升。更合理的做法是按任务或节点分配模型：复杂任务、高精确度任务使用验证过的强能力模型；简单任务使用轻量模型。

**③ 稳定运行：模型不仅要完成任务，还要持续支撑业务**

测试时效果好不代表放量时仍然可用。选型时也要综合考虑并发容量、请求和 Token 限额以及部署方式。大公司的服务保障和基础设施可以作为参考，但也不能仅凭厂商品牌判断稳定性。


### 4.3 Prompt 撰写：填平意图语言与工程语言的鸿沟

前面第三部分说过，这是生成类产品最核心的中间层。

它可以 skill 化，是因为：
- 输入明确（知道用户想要什么效果）
- 步骤可执行（判定类型 → 素材映射 → 歧义拦截 → 挂约束包 → 自检）
- 输出可验证（生成的 Prompt 能不能直接用）

→ [Prompt 撰写 skill](../skills/prompt-writing/SKILL.md)

### 4.4 效果评测：把「好不好」变成可判定的东西

C 端产品的评测通常从两个层面入手：**benchmark基础指标**和**产品侧评测指标**。难点在于**用户感受到的是整体效果，但改进必须落到具体环节。**

只打总分知道好不好但不知道改哪里；只看节点技术指标每个都达标但合起来还是不好看。所以需要按维度拆解，并且给每个维度写可判定的锚点描述。

这一层能 skill 化，是因为「拆维度 → 定判定标准 → 算一致率 → 看失败模式分布」这个流程本身是高度可迁移的，换产品换场景都适用。

→ [效果评测框架](../skills/evaluation/SKILL.md)
