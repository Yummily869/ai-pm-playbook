# 模型选型

## 这个 skill 解决什么

产品做模型选型时最容易犯两个错误：

**错误一：用榜单代替评测。** 把 Chatbot Arena 或 Hugging Face 的通用 benchmark 当选型依据。通用 benchmark 测的是平均水平，你的产品场景是具体的——商业图的中文文字渲染、竖屏视频的人物一致性、实时配音的首包延迟，这些都不在通用榜单里。

**错误二：只看效果，忘了约束。** 某个模型效果最好，但国内无法直接访问；或者单次成本比竞品高 5 倍；或者供应商没有数据隔离协议——这些约束应该**先于**效果判断。

---

## 这个 skill 的结构：方法与数据分离

```
model-selection/
├── SKILL.md              ← 方法层：怎么选（本文件，长期有效）
└── benchmarks/
    └── 2026-09.md        ← 数据层：现在有什么（时间快照，会过期）
```

**为什么要分开**：模型迭代极快，一份写死模型名和价格的文档三个月后就是错的，而且因为看起来权威反而会误导。

分开之后：
- **判断逻辑**（「需要 15s 以上叙事 → 找最长时长 ≥15s 的模型」）永远成立
- **具体答案**（「哪个模型支持 15s」）去快照里查，过期就换新快照

**使用本 skill 时**：先读方法层建立判断框架，再去 `benchmarks/` 下读**最新一份**快照获取候选。若快照日期距今超过 3 个月，必须联网核实关键参数。

## 执行流程

### Phase 0：解析输入，一次性澄清

收到输入后，先判断以下信息是否已知。**只问一次**，未回答的字段标记为「未明确」，不阻塞后续分析。

| 信息 | 若未知则询问 |
|------|------------|
| 场景类型 | 文生图 / 文生视频 / 视觉理解 / TTS / 文本生成 / 其他？ |
| 具体用途 | 生成什么内容，给谁用，在产品链路的哪个位置？ |
| 硬约束 | 国内是否必须可用？数据合规要求？延迟上限？成本上限？ |
| 调用量级 | 日调用量大致是什么量级？（决定成本权重）|
| 决策目的 | 产品集成（要结论）还是竞品调研（要全景）？ |

---

### Phase 1：约束过滤（先砍后选）

**这一步必须在看效果之前完成**，否则会在不可能选的模型上浪费时间。

| 约束类型 | 要问的问题 | 不满足则直接排除 |
|---------|----------|----------------|
| **API 可用性** | 国内能否直接调用？是否需要白名单或企业资质？是否有官方 RESTful API？ | 无国内节点且无法合规绕行；或根本没有 API |
| **数据合规** | 用户数据是否会被用于训练？是否有企业级数据隔离协议？是否需要 AIGC 服务备案？ | 产品涉及用户隐私数据但供应商无隔离协议 |
| **延迟要求** | 同步交互（需 <2s）还是异步生成（可接受 >30s）？ | 模型延迟远超场景容忍上限 |
| **成本上限** | 日调用量 × 单价是否在预算内？ | 超出预算 3 倍以上 |
| **供应商稳定性** | 有公开 SLA 吗？有宕机历史吗？能签合同锁价吗？ | 核心链路无法承受服务中断 |

> **举例说明这一步的价值**：Midjourney 在文生图的视觉质量上评价很高，但截至 2026-09 仍没有官方 RESTful API，只能通过 Discord Bot 调用。对需要程序化批量生成的产品来说，它在 Phase 1 就该被排除，根本不需要进入效果对比。

---

### Phase 2：确定场景专项维度

不同场景的关键维度完全不同。先确定「这个场景要看什么」，再去查「哪些模型满足」。

#### 文生图

先区分用途，不同用途的第一关注维度不同：

| 用途 | 第一维度 | 第二维度 | 容易忽视的坑 |
|------|---------|---------|------------|
| 商业图（电商/门店/营销）| **中文文字渲染准确性** | 参考图风格可控性 | 内容安全策略对商品图的误伤 |
| C 端创意图 | 风格多样性 / 人物保真 | API 稳定性 | 肖像权、换脸政策 |
| 批量素材 | 输出稳定性（同 prompt 方差）| 批量计费折扣 | 只测了平均质量，没测方差 |
| IP / 角色一致性 | 参考图控制能力 | 跨图人物一致性 | 是否需要私有部署 |

> **中文文字渲染是国内商业图场景最高频的坑**。多数模型对中文的渲染质量远低于英文，常见字形扭曲、笔画缺失、位置偏移。必须专门准备带中文文字的测试用例。

#### 文生视频

| 维度 | 说明 | 为什么重要 |
|------|------|----------|
| **时长上限** | 单次生成秒数，是否支持延长 | 直接决定能承载什么叙事结构 |
| **运动自然度** | 人体动作、镜头运动、物理效果 | 低质模型在运动时手部/面部会崩塌 |
| **可控性** | 同 prompt 多次生成的结果方差 | 「抽卡型」模型无法用于稳定工作流 |
| **参考输入能力** | 首尾帧、人物参考图、风格参考 | 品牌/IP 内容的必要能力 |
| **原生音频** | 是否同时生成配套音效/对话 | 有则省去后期合成步骤 |
| **成本结构** | 按秒计费；是否有 Fast/Pro 双档 | 大规模生产时成本差异可达 10 倍 |

> **举例说明「时长」为什么是硬维度**：Seedance 2.5（2026-07 发布）把单次时长从 15s 提到 30s。15s 只够一个氛围片段；30s 才装得下「铺垫→推进→转折→收尾」。这类**参数级跃迁**才是真正改变产品可能性的分界线，而不是「画质提升了」这种模糊描述。
>
> ⚠️ 上述为举例说明维度重要性，不构成推荐。当前各模型的具体时长请查 `benchmarks/`。

> **关键坑：不要只看官方 demo**。各厂商 demo 均经过精选 prompt 和多次重试。必须用你真实的产品场景 prompt 测试，并**多次运行看方差**，而非只看单次最佳结果。

#### 视觉理解（VLM）

先分清任务类型，两类的选型逻辑截然不同：

| 任务类型 | 说明 | 代表场景 | 对模型的要求 |
|---------|------|---------|------------|
| **识别型**（看图说话）| 描述画面、识别物体/文字 | OCR、商品识别 | 小参数模型通常够用 |
| **推理型**（看图做判断）| 基于视觉做逻辑推断 | 高光识别、内容审核、剪辑思路 | 需要大参数模型的推理能力 |

| 维度 | 说明 |
|------|------|
| **多帧 / 视频理解** | 能否理解时序关系，还是只会看单帧 |
| **结构化输出稳定性** | JSON 格式是否稳定——Agent 流程里这比能力上限更关键 |
| **中文语境理解** | 中文字幕、中文语境下的情绪/动作描述 |
| **视觉 token 成本** | 帧数多则成本高，且各模型计费方式差异大，**无法跨模型直接比价** |

#### TTS 语音合成

TTS 的典型陷阱是：demo 试听很好，上线后真实场景（长文本、数字读法、停顿节奏）问题频出。

| 维度 | 说明 | 高频踩坑点 |
|------|------|----------|
| **自然度（MOS）** | 盲听主观评分 | 只测短句；日常对话自然但播报体很机械 |
| **首包延迟** | 请求到第一段音频返回 | 实时对话要求 <300ms，配音可接受 >1s |
| **声音克隆** | 所需参考音频时长 | 克隆质量在情绪变化、快语速时急剧下降 |
| **中文质量** | 多音字、人名地名、停顿节奏 | 英文优先的模型音色好但中文韵律不自然 |
| **长文本稳定性** | 几千字是否忘词、重复、语速异常 | 多数模型只测过 200 字以内 |
| **成本计费口径** | 按字符还是按字节 | **按 UTF-8 字节计费的服务，中文成本是英文的 2-3 倍** |

#### 文本生成（LLM）

先明确任务类型，不同任务的关键维度不同：

| 任务类型 | 典型场景 | 关键维度 |
|---------|---------|---------|
| 创意写作 | 文案、故事、台词 | 创意多样性、风格可控性 |
| **结构化输出** | JSON 提取、Agent 中间步骤 | **格式遵循稳定性**、函数调用能力 |
| 长文理解 | 脚本分析、文档总结 | 上下文窗口、长文一致性 |
| 推理任务 | 内容审核、评分、决策 | 逻辑推理能力 |
| 对话 / Agent | 客服、助手 | 指令遵循、多轮上下文、工具调用 |

> **「上下文窗口大」≠「长文理解好」**。多数模型在超过窗口 50% 后性能显著下降，必须专项测试而不是看标称参数。

### Phase 3：查基准表 + 联网补充

**Step 1**：读 `benchmarks/` 目录下**日期最新**的快照文件，按 Phase 2 确定的维度筛选候选。

**Step 2**：检查快照日期。

```
距今 ≤ 3 个月  → 可直接使用，但价格仍建议核实
距今 > 3 个月  → 必须联网补充，快照仅作为「有哪些候选」的起点
```

**Step 3**：使用 `search_web` 补充新发布模型。搜索建议：

```
"{场景类型} model 2026 latest release comparison"
"{场景类型} 模型 最新 发布 对比"
"{候选模型名} pricing API documentation"
```

**Step 4**：对用户明确提到的模型，单独搜索最新能力参数和定价。

> ⚠️ **对快照数据的正确态度**：快照里的 ★ 评分是综合公开信息的判断，**不是实测数据**。它只能用来缩小候选范围，不能作为选型结论。

---

### Phase 4：核算真实成本

单价不等于真实成本。

```
真实成本 = 单次调用成本 × (1 + 失败率 × 重试次数)
         + 后处理成本（是否需要再调一次模型修正输出）
         + 工程接入成本摊销
         + 迁移成本（未来换模型有多痛）
```

> **举例**：一个「便宜 50%」的模型，如果失败率高到需要平均重试 2 次，实际成本反而高于贵的那个。这个差异只有实测才能发现，看定价表看不出来。

**成本估算模板**：

| 项目 | 模型 A | 模型 B |
|------|-------|-------|
| 单次调用单价 | | |
| 实测失败率 | | |
| 平均重试次数 | | |
| 是否需要后处理 | | |
| **折算后单次真实成本** | | |
| 日调用量 | | |
| **日成本** | | |

---

### Phase 5：评估供应商风险

这一层最容易被忽视，但在核心链路上最致命。

| 风险类型 | 要确认的事 |
|---------|----------|
| **单点依赖** | 全部流量压在一个模型上，它宕机/涨价怎么办？有没有备选？ |
| **服务稳定性** | 公开 SLA 是多少？历史宕机记录？ |
| **定价稳定性** | 当前是不是优惠期价格？能否签合同锁价？ |
| **版本生命周期** | 供应商会不会突然下线某个版本？历史上有过吗？ |
| **数据条款** | 输入数据的留存期、是否用于训练、能否要求删除 |

> OpenAI 历史上多次下线旧模型版本，导致依赖该版本的产品被迫紧急迁移。选型时就应该问：如果这个版本明天下线，我的替代路径是什么？

---

### Phase 6：输出选型建议

根据 Phase 0 确定的决策目的：

- **产品集成型**：输出「主推 + 理由 + 备选 + 降级方案」四件套
- **竞品调研型**：输出全景对比表，不强制结论，但标注每个模型的最优适用场景

**降级方案必须写**。至少回答：主推模型不可用时，用什么顶上，效果会降到什么程度。

## 决策树的正确用法

决策树只放**判断逻辑**，具体模型名去快照里查。这样即使快照过期，逻辑依然成立。

**文生视频示例**：

```
需要 15s 以上完整叙事？
├── 是 → 查快照中「最长时长 ≥ 15s」的模型
└── 否 → 继续：
    需要中文口播唇形同步？
    ├── 是 → 查快照中标注「中文口播同步」的模型
    └── 否 → 继续：
        质量优先还是成本优先？
        ├── 质量优先 → 查快照中价格最高档、评分最高的模型
        └── 成本优先 → 查快照中价格最低档、仍满足分辨率要求的模型
```

**TTS 示例**：

```
有国内数据合规要求？
├── 是 → 只在快照「国内服务」表中选
└── 否 → 继续：
    实时对话场景（延迟 <300ms）？
    ├── 是 → 查快照中「首包延迟 <300ms」的模型
    └── 否 → 继续：
        需要声音克隆？
        ├── 是 → 查快照中支持克隆的模型，对比所需参考音频时长
        └── 否 → 按成本排序选择
```

**通用结构**：`硬约束 → 场景专项能力 → 质量/成本取舍`，永远是这个顺序。

## 与评测的衔接

**本 skill 输出的是「候选收敛结论」，不是「最终选型结论」。**

真正的选型结论必须用你自己的场景数据跑评测得出。评测集怎么构造、评分标准怎么定、一致率怎么保证，见 [`../evaluation/SKILL.md`](../evaluation/SKILL.md)。

两者的分工：

```
model-selection  →  从 10+ 个模型收敛到 2-3 个候选
       ↓
evaluation       →  用真实场景数据跑评测，选出最终方案
```

跳过评测直接用本 skill 的结论上线，是对这份文档的误用。

## 我还没搞清楚的

- **视觉理解的成本横向比较**：不同模型对视频帧的 token 计算方式差异太大，目前没找到可靠的换算方法，只能用真实素材各跑一遍
- **中文 TTS 的独立评测**：现有中文 TTS 数据多为厂商自测，SuperCLUE-TTS 这类独立评测更新频率不稳定
- **国内模型的企业级 SLA**：公开文档描述普遍模糊，实际保障级别只能通过商务谈判确认
- **「可控性/方差」缺少标准化测量方法**：知道它重要，但同一 prompt 跑多少次、怎么量化方差，目前没有行业共识
