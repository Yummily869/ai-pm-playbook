# AI 产品评测框架

---

## 一、为什么评测，以及行业通行做法

### 1.1 AI 产品的核心评测矛盾

传统软件功能可以用单测覆盖：输入固定，输出确定。AI 产品的问题在于：

- **输出是开黑盒**，同一个输入多次运行可能得到不同结果
- **正确答案不唯一**，图像美不美、回答好不好，没有绝对标准
- **链路长，节点多**，最终效果差不知道是哪个环节的问题

这导致「AI 产品好不好」这个问题很难用技术指标直接回答，必须建立专门的评测体系。

**评测的核心价值有三个：**

| 用途 | 解决什么问题 |
|---|---|
| 建立基线 | 知道现在是什么水平，有了比较的起点 |
| 驱动迭代 | 改了 Prompt 或换了模型之后，用数据说明是否真的变好了 |
| 放量判据 | 灰度时有定量依据决定「可以扩量」还是「需要先修复」|

### 1.2 行业通行的评测类型

**① Benchmark 评测**

针对模型能力的标准化测试集，用于横向比较不同模型。

| Benchmark | 评什么 | 适用场景 |
|---|---|---|
| MMLU | 多领域知识（57 个学科） | 判断 LLM 的知识覆盖度 |
| HumanEval / MBPP | 代码生成能力 | 选代码辅助类模型 |
| MT-Bench | 多轮对话质量 | 选对话类 LLM |
| FID（Fréchet Inception Distance） | 生成图像与真实图像的分布差距 | 选图像生成模型 |
| CLIP Score | 图像与文本描述的语义对齐程度 | 评测图生文/文生图的对齐质量 |

**Benchmark 的局限**：它评的是模型通用能力，不是你的产品场景能力。一个 MMLU 得分很高的模型，可能在你的特定垂类任务上并不比得分低的模型好。Benchmark 用来做初筛，不能替代产品场景评测。

**② 产品场景评测**

用用户的数据、产品的标准，评测模型在真实使用场景下的表现。这是本文档的重点。

**③ 自动化评测 vs 人工评测**

| 方式 | 优点 | 缺点 | 适合场景 |
|---|---|---|---|
| 规则指标（准确率、召回率、BLEU） | 快速、可重复、零成本 | 只能评有客观答案的任务 | 结构化输出、分类任务 |
| LLM-as-Judge | 可处理开放式输出，规模化 | 受评测 LLM 自身偏见影响 | 文本质量、指令遵循度 |
| 人工评测 | 最贴近真实用户感受 | 慢、贵、标注一致性难保证 | 建立基线、校准自动化评测 |
| 混合方式 | 兼顾效率和质量 | 需要维护两套流程 | 大多数产品的生产评测 |

### 1.3 不同产品形态，评测重心不同

核心原则：**评测维度应该直接对应产品的核心价值主张**，而不是套用通用框架。

| 产品形态 | 核心价值主张 | 评测重心 |
|---|---|---|
| **对话式 AI（客服/助手）** | 回答准确、不出错、能解决问题 | 事实准确率、幻觉率、拒答率 |
| **AIGC 内容（生图/生视频）** | 效果符合预期、有美感 | 指令遵循度、视觉质量、内容一致性 |
| **Agent（多工具调用）** | 任务完成、调用路径合理 | 任务完成率、工具调用准确率、冗余率 |
| **搜索/推荐增强** | 找得到、找得准 | 召回率、排序质量、相关性 |

## 二、不同产品形态的评测实践

### 2.1 Agent 类：以**商家claw**多 skill Agent 为例

**产品背景**

商家 Claw 是一个面向电商商家的多 skill Agent，商家输入经营相关问题（如「最近外卖订单下降，怎么回事？」），Agent 需要判断调用哪些 skill（销售数据查询、差评分析、竞品对比、营销建议等），结合该商家自身的经营数据给出针对性的分析和建议。

**为什么 Agent 评测不能只看「任务完成了没」**

假设任务完成率 80%——你不知道剩下 20% 是因为：
- 根本没找到对的 skill（意图识别错了，问的是订单问题却去调了评价分析 skill）
- 找到了对的 skill 但参数传错了（查的是全平台数据而不是这家商家的数据）
- 调用了对的 skill 但还额外调用了一堆无关的 skill，把不相关数据混进了分析结论
- skill 都调对了，但最终答案是通用建议，没有结合这家商家的实际情况

这四种失败需要不同的修复方式，所以需要分开评测。

**商家 Claw Agent 的评测维度**

| 维度 | 定义 | 为什么重要 |
|---|---|---|
| **任务完成率** | 用户意图最终是否被正确满足 | 最终产品价值指标，所有其他维度都服务于此 |
| **Skill 召回率** | 任务所需的关键 skill 是否都被调用 | 必要的 skill 没被调用，分析必然不完整——商家问订单下降，若没调销售趋势 skill，结论无从谈起 |
| **Skill 精确率** | 被调用的 skill 中有多少是任务真正需要的 | 冗余调用不仅增加延迟、消耗 token，还会把无关数据混进分析，干扰最终结论 |
| **Skill 匹配度** | 被调用的 skill 是否是最合适的那个（而不是「能用但不最优」的） | 防止用通用数据查询代替专门的销售趋势分析 skill——数据能出来，但缺少趋势计算和异常识别 |
| **调用参数准确率** | 传给 skill 的参数是否正确（如时间范围、商家 ID、数据维度） | skill 选对了但参数错了，查的就不是这家商家自己的数据，结果完全不可用 |
| **答案可用性** | 最终答案是否结合了用户问题与该商家自身数据，给出有针对性的分析和建议，而非泛泛而谈 | 这是商家 Claw 区别于通用 LLM 的核心价值：商家要的不是「外卖订单下降的通用原因」，而是「你家上周四开始下降，主要是差评里反复提到打包汤汁漏的问题」 |

**评分方式**

```
任务完成率：二值判断（完成/未完成），由人工或 LLM-as-Judge 评判
Skill 召回率 = 正确调用的 skill 数 / 任务实际需要的 skill 总数
Skill 精确率 = 正确调用的 skill 数 / 实际调用的 skill 总数
Skill 匹配度/调用参数准确率：人工抽样标注，建立基线后可用 LLM-as-Judge 扩大规模
答案可用性：人工评测为主（判断答案是否真正用了商家自身数据、是否给出了可执行建议）
```

**通过这套维度可以定位根因**

| 失败模式 | 对应指标下降 | 修复方向 |
|---|---|---|
| 找不到对的 skill | Skill 召回率低 | 改进意图识别、丰富 skill 描述 |
| 调用了一堆无用 skill | Skill 精确率低 | 加约束条件、改 Agent 提示词 |
| skill 选了近似的而不是最优的 | 匹配度低 | 优化 skill 之间的语义边界描述 |
| skill 选对了但参数传错了 | 参数准确率低 | 改参数提取 Prompt，明确商家 ID、时间范围等关键参数的提取规则 |
| skill 都调对了但答案是通用建议 | 答案可用性低 | 检查汇总 Prompt 是否要求模型引用具体数据；检查 skill 返回的结构化数据是否被正确传递给汇总节点 |

### 2.2 AIGC 内容类（生图）

**产品背景**

面向美发类商家，为其自动生成两类核心经营素材：一是门店入口图——门店列表页/详情页头图，用户在浏览列表以及点进页面时第一眼看到的图；二是团单图，团购套餐的商品图，用户点进详情后决定是否下单

**为什么生图评测不能只看「图好不好看」**

如果只评美观度，很容易生成一张视觉上精美但内容完全不对的图——比如用户要「红烧肉」，生成了一道牛排。对商家来说，这张图没有任何使用价值，因为它会误导用户对实际菜品产生错误预期。

**美团生图的评测维度**

| 维度 | 定义 | 为什么这个维度决定了产品价值 |
|---|---|---|
| **指令遵循度** | 生成图与输入描述的匹配程度 | **最高优先级**。图再好看，不对就不能用。要求「齐耳短发」，出来「及腰长发」，直接判废 |
| **主体完整性** | 头发主体与人物是否完整合理呈现| 发型图必须让人看清完整形态；人脸变形属于更严重的可用性问题 |
| **文字准确性** | 图中若有文字（门店名、价目、标签、发色色号），是否正确无误、清晰可读 | 文字错误是门店不可接受的硬性缺陷，一旦出现直接影响采用率 |
| **主体完整性** | 菜品是否完整出现在画面中、无截断或遮挡 | 决定图的可用下限。假发套感、糊成一片的发丝无法被采纳 |
| **主观美学** |整体视觉吸引力：造型氛围、色彩、时尚感，是否让人产生「我就想用这张图」的冲动 | 决定图的商业价值——同一个发型，吸引力高的图预约转化更高 |
| **内容安全** |是否包含违规或引起不适内容，是否有信息安全泄漏| 一票否决。不仅有合规风险，肖像权问题在美发场景里尤其敏感 |

**维度权重逻辑**

```
第一层：准入门槛
指令遵循度低于 X 分直接判定不可用，不参与后续加权
内容出现违规，直接判定不可用

第二层：加权评分
文字准确性-25%
图像呈现-25%
主观美学-25%
主体完整性-25%
```


**实际评测中发现的典型失败模式**

| 失败类型 | 在哪个维度会体现 | 根因 |
|---|---|---|
| 脸部五官扭曲、多眼多指| 主体完整性低 | 人物结构生成不稳定 |
| 图中文字错乱、乱码 | 文字准确性低 | 模型文字渲染能力不足，缺少生成后校验 |
| 发色对不上（要冷棕给金发） | 指令遵循度低 | 颜色类词汇缺少量化锚点，模型自由发挥 |
| 背景／氛围过度精美导致人物被弱化 | 主观美学高，但指令遵循度、主体完整性低| Prompt 过度强调「美观」，模型忽略主体约束|

## 三、怎么做评测

### 3.1 构造评测集

**原则一：覆盖输入分布，而不是只覆盖典型案例**

典型案例只能告诉你「正常情况下能不能用」。评测集需要覆盖：

| 输入类型 | 用途 |
|---|---|
| 典型输入（核心场景，占比 50%） | 验证基础能力 |
| 边缘输入（长尾、模糊、歧义，占比 30%） | 找稳定性问题 |
| 对抗输入（容易让模型出错的输入，占比 20%） | 找失败模式 |

**原则二：评测集大小取决于你需要检测的效果变化粒度**

| 想检测的变化 | 需要的样本量 | 理由 |
|---|---|---|
| ±5% 的准确率变化 | ≥ 200 条 | 统计显著性要求 |
| ±10% 的准确率变化 | ≥ 50 条 | 可行的小样本评测 |
| 功能有没有大范围失效 | 20-30 条覆盖主路径 | 快速健康检查 |

**原则三：评测集需要标注 Ground Truth**

- Ground Truth 怎么来：专家标注（贵、准）/ 规则生成（快、覆盖面窄）/ 历史人工审核数据（有一定噪声但量大）
- Ground Truth 质量检验：抽样让第二个标注者重标，计算一致率，一致率低于 80% 说明标准本身有歧义，需要先修订标准再重新标注

**原则四：评测集要和训练集/微调集隔离**

用于微调的数据不能出现在评测集里，否则评测结果会虚高。

### 3.2 制定评分标准

**两种标准形式**

| 形式 | 适合场景 | 示例 |
|---|---|---|
| **二值判断**（通过/不通过） | 有明确对错的任务 | 生成的 JSON 格式是否合法；菜品名称是否出现在图中 |
| **多级评分**（1-5 分或 0-10 分） | 开放式质量评估 | 图像美观度；视频叙事完整性 |

**多级评分的写法**：每个档位必须有可判定的锚点描述，不能只写数字。

❌ 错误写法：
```
1-3 分：差
4-6 分：一般
7-10 分：好
```

✅ 正确写法（以「食物真实感」为例）：
```
1-3 分：有明显 AI/3D 渲染感，食物纹理失真，或颜色不自然（如肉类显示塑料光泽）
4-6 分：整体看起来像真实食物，但某些细节有失真（如汤汁反光过度、蔬菜边缘过硬）
7-8 分：外观接近真实菜品，细节处理自然，偶有轻微瑕疵
9-10 分：难以与真实菜品照片区分，纹理、光线、颜色高度真实
```

档位描述的关键：**可观察的具体特征**，而不是主观感受词。

**确立人工标注一致率**

在正式评测前，让 2-3 人分别对同一批样本打分，计算一致率：

```
一致率 = 打分完全一致的样本数 / 总样本数

一致率 ≥ 80%：标准可用
一致率 60-80%：标准需要进一步细化，特别是争议样本需要讨论并更新锚点描述
一致率 < 60%：标准存在根本性歧义，需要重新设计
```

### 3.3 评测执行

**自动化优先，人工兜底**

推荐的混合方案：

```
Step 1：自动化跑全量评测集，得到分数分布
Step 2：人工复核自动化评分「存疑区间」（通常是中间分数段，如 4-6 分）
Step 3：对失败样本人工分析根因，不要只看平均分
```

**LLM-as-Judge 的使用注意事项**

- 用更强的模型评测更弱的模型输出（或同级但不同产品线的模型）
- 评测 Prompt 要包含：评分标准锚点 + 禁止说废话只输出 JSON + Few-shot 示例
- 定期抽样人工校验 LLM 评分的准确率，防止评测漂移

**人工评测的操作要点**

- 评测者不知道哪个是 A 方案哪个是 B 方案（盲评）
- 给相对判断（A 优于 B / 相当 / B 优于 A）往往比绝对打分更一致
- 记录所有「争议样本」，它们是改进标准的依据

### 3.4 用好评测结果

**看失败模式分布，不要只看平均分**

平均分 7.2 和平均分 7.2 可能代表两种完全不同的情况：

```
情况 A：所有样本都在 6-8 分，效果稳定但中等
情况 B：60% 的样本 9-10 分，但 20% 的样本 1-2 分，有严重失效的 case
```

情况 B 的产品感知可能比情况 A 更差，因为用户对低分 case 的记忆远强于高分 case。

**失败模式分类方法**

1. 抽取所有低分样本（如 < 5 分）
2. 人工阅读后按根因聚类：指令理解错误 / 模型能力边界 / 数据质量问题 / Prompt 设计问题
3. 按类别统计占比
4. 优先修复占比最大的类别

**评测指标与产品指标挂钩**

评测指标只有和产品结果连接才有意义：

| 评测维度 | 对应产品指标 | 连接方式 |
|---|---|---|
| 指令遵循度 | 用户采用率（生成的内容用户是否真的用了） | 低遵循度 → 生成结果频繁被用户重新生成或放弃 |
| 高光识别准确率 | 导出率、分享率 | 高光选错 → 用户觉得结果没用，不会导出 |
| Agent 任务完成率 | 功能使用深度（用了几次之后还在用） | 完成率低 → 用户快速流失，回到手动操作 |

## 附：常见评测坑

| 坑 | 表现 | 规避方法 |
|---|---|---|
| 评测集不代表真实分布 | 模型在评测集上效果好，上线后 badcase 大量出现 | 从线上真实流量中抽样，而不是手工构造 |
| 维度之间权重加总但掩盖了关键失败 | 某个致命维度只有 2 分，但被其他维度平均拉高到 6 分 | 关键维度设「一票否决」门槛，不参与平均 |
| Ground Truth 由同一个人制定和评测 | 评分标准向自己的直觉偏移，最终评测只是验证了自己的感受 | 标准制定和评测执行隔离，或引入第三方标注 |
| 只评测 happy path | 边缘输入、错误输入被忽略 | 专门构造一批对抗样本，单独统计稳定性指标 |
| 模型迭代后不重跑历史评测集 | 新版本修复了 A 问题但引入了 B 问题，没有被发现 | 建立回归评测机制，每次迭代都跑标准评测集 |
